## Why this plan exists

The third programme on the shared tracker section: the maintainer named a
full-stack console — button-press script launching, interactive
drill-down (canonically: list SQS queues → dump → pretty JSON → select
field values → DynamoDB query by PK → decide how to proceed), and
comprehensive audit + self-monitoring. A five-facet audit confirmed the
baselines have the right seams and none of the service substrate (no
HTTP server, daemon, registry, streaming, sessions, frontend toolchain,
containers, human-action audit), plus one fleet gap (sqs-etl has no
list-queues) and one design conflict (UI display vs redaction stances)
resolved by ADR-0070's display-vs-persist rule. Eight ADRs record the
decisions; this plan decomposes them into X1–X16.

## Scope and sequencing

| Stage | Contents                                                              | Shape                                                                                   |
| ----- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **1** | X1 docs; X2 server skeleton; X3 persistence; X5 fleet PR              | Foundation; independently shippable                                                     |
| **2** | X4 run orchestration; X9 web skeleton; X10 run-launcher MVP           | First end-to-end value — **spawn-only until U7**, so nothing here waits on the U-series |
| **3** | X6 workbench sessions; X11 drill-down UI                              | The flagship; X11's e2e acceptance is the SQS scenario                                  |
| **4** | X7 audit + correlation; X8 telemetry; X12 containers; X13 flow export | Hardening + the containerized shape                                                     |
| Gated | X14 remote/multi-user; X15 microservice split; X16 Aurora             | Recorded; each behind its named unblock                                                 |

**Cross-programme edges.** U3/U6/U7 are hard only for the _in-process_
path (X4's spawn path serves all fourteen scripts from day one; live
output degrades to spawn log-tailing until U7). U4/U8 soften into richer
parameter forms and operation pickers. **U10 consumes X6's binding
convention** — the reversed dependency recorded in ADR-0056's Update;
X13 coordinates with U10's status when it starts. V6/V7 integrate behind
ADR-0065's escalate-by-default posture until they ship. A2's grading
prerequisite applies through the same policy posture. W-series untouched.

Every code row writes into `packages/*/src/**`, `scripts/*/src/**` or
`**/tests/**`, so each begins with `/starting-work` and dispatches
`code-implementer` / `test-author` — the hub never writes those paths.

## Stage 1 — foundation

### X1. Console decisions and governance docs — this change set

ADR-0064…0071, the four Update/amendment blocks, index rows, this plan,
tracker rows, ROADMAP subsection, filing-work legend. No code.

### X2. `m3l-console-server` skeleton

**Decisions:** ADR-0065, ADR-0071. Package registration (root tsconfig
reference, knip, ESLint module-boundary zones, coverage), `node:http`
entry + internal router (framework fallback recorded in 0065),
health/readiness endpoints, service env-config conventions, the
auth/session middleware seam with the single-operator identity provider
(declared operator profile required), graceful drain via the ADR-0049
caller path. New private 0.x package.

### X3. Persistence foundation

**Decision:** ADR-0069. `node:sqlite` behind typed repository
interfaces; schema/migration convention; **the stability checkpoint** —
confirm the builtin's API against the Node 24 floor, with the recorded
fallback options (accept a packaged sqlite dep via a dated 0069 Update,
or degraded JSONL-only mode) exercised only on failure.

### X5. `sqs-etl` list-queues operation

**Decision-recorded gap:** ADR-0064. A small fleet PR adding the missing
`list-queues` operation (ADR-0055-declarative once U4 ships; `oneOf`
until then) — the drill-down's first step. Independent of everything
else; can land any time.

## Stage 2 — first end-to-end value

### X4. Run orchestration module

**Decisions:** ADR-0065, ADR-0066. The run registry (store-backed),
per-script mutex + bounded queue + global cap, spawn path first
(in-process via the ADR-0054 seam when U7 lands), SSE run-progress and
log-tail channels with the ring-buffer resume semantics, policy/audit
wiring points (escalate-by-default until V6/V7). Registry is
console-owned; `m3l history` remains CLI-only (0065's recorded
asymmetry).

### X9. `m3l-console-web` skeleton

**Decision:** ADR-0067. Vite + React 19 + TS strict; per-package DOM
tsconfig; JSX/browser ESLint zones; Vitest browser-env unit tests;
Playwright harness (the CI-cost decision — scoped or label-gated job —
is made and recorded in this row's PR). New private 0.x package.

### X10. Run-launcher UI MVP

**Decisions:** ADR-0066, ADR-0067. Script list (discovery), parameter
form (introspection; richer with U4/U8), launch button, live SSE
progress/log tail, run registry views. **The "press of a button" moment
— explicitly not blocked on U7** (spawn + log-tail is the degraded but
shippable mode).

## Stage 3 — the flagship drill-down

### X6. Workbench sessions module

**Decision:** ADR-0068. Session model, addressable step results
(reference grammar fixed here), typed field-selection bindings,
decision points, resume, artifact-file storage with caps; **the
convention U10 consumes** — coordinate its type home (console-local
now; m3l-common promotion triggered by U10 starting).

### X11. Drill-down UI

**Decisions:** ADR-0068 (+0067). JSON tree viewer with value selection →
binding creation → parameter-form pre-fill → next operation; decision
prompts. **Acceptance: the canonical SQS scenario end-to-end under
Playwright** — list queues (X5) → dump → select field values → DynamoDB
query by those keys → operator decision — the programme's defining test.

## Stage 4 — hardening

### X7. Human-action audit + correlation threading

**Decision:** ADR-0070. The append-only human-action stream (+ SQLite
index), operator identity in every record, view-action auditing,
`AsyncLocalStorage` request context threading the correlation id into
`M3LScript.run()`'s existing `correlationId` (a missing library seam =
flagged m3l-common additive-minor decision here).

### X8. Self-telemetry + retention

**Decision:** ADR-0070. Route/script/SSE/policy metrics into the store;
telemetry query endpoints (the UI's monitoring pages); declared
retention policies per artifact class + the operator-run cleanup
command.

### X12. Containerization + compose

**Decision:** ADR-0071. Two images (non-root), compose with health
wiring and stop-signal drain, `data/` volume, host-SSO credential
volume-pass; **fires the deferred ADR-0015 Update** ("ships no images")
and the image-scanning reassessment in the same PR.

### X13. Session → flow export

**Decision:** ADR-0068. Export a session as an ADR-0056 flow definition
using the shared X6/U10 convention; coordinate with U10's state at
execution time.

## Documentation reconciliation

Console packages are **not** counted submodules — the doc-count gates
stay no-ops throughout; console reference docs (API contract, session
concept, deployment guide) arrive per shipped row under
`docs/reference/` with sidecars then, via `/syncing-docs`. The U10 row's
Source/notes pointer to ADR-0068 lands in X1. No reserved CLI command
names are claimed.

## Definition of done

- X1 (docs wave): `pnpm verify` green; tracker/hub-key gates clean;
  doc-count/index/provenance gates no-ops; `pnpm sync:hub` dry-run
  reviewed, applied post-merge.
- Code rows: the standard battery (`typecheck`, `lint`, `test:coverage`
  thresholds, `build`, `check:zones` with no zone widened beyond the
  new console zones' own additions, `check:api`/`check:exports`
  unchanged, package/scaffold gates for the new packages), `pnpm verify`
  reproducing CI; trackers flipped; a work log per shipped stage.
