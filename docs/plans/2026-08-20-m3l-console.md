## Why this plan exists

The third programme on the shared tracker section: the maintainer named a
full-stack console — button-press script launching, interactive
drill-down (canonically: list SQS queues → dump → pretty JSON → select
field values → DynamoDB query by PK → decide how to proceed), and
comprehensive audit + self-monitoring. A five-facet audit confirmed the
baselines have the right seams and none of the service substrate (no
HTTP server, daemon, registry, streaming, sessions, frontend toolchain,
containers, human-action audit), plus one fleet gap (sqs-etl has no
list-queues) and one design conflict (UI display vs redaction stances)
resolved by ADR-0070's display-vs-persist rule. Eight ADRs record the
decisions; this plan decomposes them into X1–X16.

## Stage 4 — hardening

### X7. Human-action audit + correlation threading

**Decision:** ADR-0070. The append-only human-action stream (+ SQLite

### X8. Self-telemetry + retention

**Decision:** ADR-0070. Route/script/SSE/policy metrics into the store;
telemetry query endpoints (the UI's monitoring pages); declared
retention policies per artifact class + the operator-run cleanup
command.

**X8b design (ADR-0102; fires the trigger ADR-0070's 2026-09-05 Update
named and its 2026-09-05 second Update gave an owner).** Slice 5a-ii shipped `listSegments()` and a report-only fourth
cleanup section, so the trail's footprint is _observed_ but still
unbounded — and it cannot survive having anything removed from it:
`assertNoSequenceGap` proves contiguity only within one date (so
intra-date deletion makes every later `read()` throw, permanently), while
whole-date deletion passes silently and leaves an archived, a
never-written and a deleted date indistinguishable. X8b ships a
**writer-sealed per-segment manifest**: one directory-wide append-only
`manifest.jsonl` (`M3L_APPEND_ONLY_MANIFEST_NAME`) whose `seal` records
carry each rotated-away segment's `entryCount`, `byteLength` and a plain
sha256 of its raw bytes, so `sha256sum <archived-segment>` re-verifies an
archive with no library involved. A per-segment sidecar is rejected
because it shares the segment's date prefix — the `rm 2026-09-*` ADR-0070
sanctions would delete the proof along with the segment; one
non-date-named file survives the glob by construction. ADR-0070's other
suggestion, a per-entry chained digest, is rejected structurally: it needs
a library-owned field inside the caller's entry, which `read()`'s
verbatim-record contract forbids, and it voids the two-writer
whole-line-interleave guarantee.

Concretely:

- Both owners of `AppendOnlyWriter` get it — `Core.M3LAppendOnlyStream`
  and ADR-0061's `internal/agent/decision-log-writer.ts` — so the
  artifact class does not split. **No new CLI**: archival stays a
  documented manual procedure, and the manifest is what makes it provable.
- A `baseline` record makes backward compatibility bounded _and_ stated:
  segments at or before it classify as `legacy` and are never
  retro-digested, because a digest taken now cannot vouch for bytes a
  pre-upgrade process wrote.
- `read()` verifies **inline and non-optionally** (manifest lookup,
  already-counted `entryCount`/`byteLength`, and sha256 over chunks it
  already reads — CPU only, no extra I/O). `verify()` is the
  `listSegments()`-shaped half: never throws, returns per-segment verdicts
  plus `unprovenBefore`. A sealed-but-absent segment is tolerated only
  when the caller supplies `onArchivedSegment`, mirroring
  `onTruncatedTail` exactly; gap classification moves **ahead** of the
  sequence-gap throw, which is otherwise preserved byte-for-byte.
- A seal is **best-effort and never fatal to the append** — ADR-0061's
  loud-write rule governs the entry, not metadata about already-durable
  bytes. Loudness relocates to bounded retry, a new `onSealFailed`
  handler on both owners, and `verify()`'s `unsealed` verdict.
- A deleted-but-sealed segment now escalates, including a date's own last
  segment and a fully deleted trail — **new** tamper detection, not a
  relaxation. Intra-date archival becomes technically safe and stays an
  explicit non-goal (custody of the archive is unaddressed): capability
  unlocked, permission withheld, filed as its own row.
- `check:file-budget` is the binding constraint, so the reader cannot
  absorb the verification wiring: a pure-move `refactor:` slice extracts
  `append-only-fs.ts` and `append-only-lines.ts` first. Slices X8b3\* and
  X8b4 stay separate because `perFile: true` coverage binds each new `src`
  file to the tests that exercise it, and retrofitting that split later is
  structurally impossible.
- **Correction (2026-09-12, after X8b2 shipped).** The planning note above
  originally added that an `internal/`-only slice would ship `src/` with
  zero coverage, because "tests exercise only the public barrel" — and used
  that to argue X8b3 could not be subdivided. That is false in this repo.
  `append-only-fs.ts` and `append-only-lines.ts` both landed in X8b2 as
  `internal/` modules reached by no barrel, each with its own direct test
  suite at 100% branch coverage, and `append-only-digest.ts` did the same in
  X8b3a. With that constraint gone, ADR-0072's preference governs instead:
  X8b3 is subdivided into **X8b3a/b/c** because as one PR it measured
  ~133,000 reviewable chars against `check:review-size`'s 75,000 soft
  target, and each part is independently reviewable.
- **Split again (2026-09-12, at X8b3c's push).** The sealer alone measured
  70,771 reviewable chars; the writer wiring X8b3c was to carry with it
  would have taken the slice past 100,000. That wiring is now its own slice
  — the same principle that produced a/b/c, applied to a measurement that
  did not exist when the a/b/c split was decided.
- **A hardening slice is inserted ahead of the wiring (2026-09-12).** A
  security review of X8b3c executed probes against built output and defeated
  the tamper-evidence property four ways: a seal pre-planted in the manifest
  before the genuine one suppresses it silently (the conflict refusal fires
  only when two claims coexist, and a forgery written first is never
  contradicted); a calendar-invalid name such as `9999-99-99-9999.jsonl`
  becomes the write-once baseline and classifies every segment `legacy`,
  killing the sweep permanently; sixty-four `0000-00-00-NNNN.jsonl` decoys
  consume the whole sweep budget; and a forward clock step makes the sweep
  digest a segment another writer is still appending to, which the module
  itself calls the worst failure this design can produce. The first three
  need an attacker who can write into the trail directory — the envelope
  ADR-0102 concedes for manifest DELETION — but they differ in kind from
  what it conceded: deletion downgrades a trail visibly, while these
  manufacture a confident verdict about bytes an attacker chose. The clock
  step needs no attacker at all. **X8b3d must merge before X8b3f**, so no
  reachable code path ever carries these windows — nothing constructs the
  sealer until the wiring lands.
- **The threat model X8b3d leaves behind (2026-09-12).** Recorded here rather
  than as an ADR-0102 Update: `docs/adr/README.md` permits an Update only
  where it executes a revisit trigger the accepted Decision already declared,
  and 0102 declared none for this. The decision itself is unchanged — what
  changed is that the code now delivers what it claimed.
  **Closed:** a `baseline.upTo` that names no segment is refused at the
  manifest's own validation boundary, so a forged baseline is a loud fatal
  read rather than a silent policy change; a baseline is never derived from a
  future-dated segment; `parseSegmentName` refuses a date that is not a real
  calendar date, which removes both the `9999-99-99` baseline poison and the
  `0000-00-00` sweep decoys; and a rotation seal now MEASURES a segment the
  manifest already names instead of skipping it, so a seal pre-planted before
  the genuine one is contradicted rather than silently honoured.
  **Narrowed, not closed:** a digest refuses a measurement of a file that grew
  during the read, which catches the common case of a clock step inducing a
  sweep of a live segment — but an append landing after the post-read stat
  still yields a seal of a prefix. The structural fix belongs to X8b3f, where
  the writer can tell the sealer never to digest its own active segment; the
  residual cross-process case is a clock-trust limitation, not a code defect.
  **Open by design:** the SWEEP still trusts the manifest as a membership
  test, so a forgery pre-planted against a segment that is swept rather than
  rotated stays undetected until `verify()` ships in X8b4. Corroborating a
  whole backlog on every cold start would turn one start-up into an unbounded
  read of the trail, which is what the sweep's budget exists to prevent.
- **A second hardening slice is inserted ahead of the wiring (2026-09-13).** A
  security review of the completed-but-unmerged wiring executed probes against
  built output and proved a window nothing had covered: the sweep's
  `datePrefix < today` rule guarantees no conforming writer can still be on a
  segment, but the ROTATION seal has no equivalent guard. With two
  `M3LAppendOnlyStream` instances over one directory — a configuration the
  class's own TSDoc advertises as supported, since `O_APPEND` makes concurrent
  writers interleave whole lines — each adopts the active segment at its real
  size and then counts only its OWN bytes. Writer A's local counter crosses
  `maxSegmentBytes`, so A rotates off the segment and seals it while writer B
  is still appending to it. The manifest then permanently claims a digest over
  a PREFIX: `sha256sum` of the archived segment cannot reproduce it, so that
  date's archival is unprovable, and X8b4's inline `read()` verification would
  classify an untampered trail `mismatched` — the false-positive-on-a-tamper-guard
  this design calls its worst failure. No amount of re-`stat`-ing at digest
  time closes it, because neither writer can see the other's bytes.
  **X8b3e closes it with evidence the rotating writer already holds.** A
  rotation now carries the byte count the writer believed the segment held;
  if the file measures larger, someone else appended, and the seal DEFERS
  rather than claims. That needs no cross-process coordination — which
  ADR-0102 deliberately does not have.
  **What deferring costs, stated correctly — the PR review caught this
  overclaim.** A first draft of this bullet said a deferred seal arrives "a
  day late, via the sweep". False: the sweep is per-INSTANCE, not per-day.
  `#sealAndSweep` flips `#swept` on its first call and returns early on every
  later one, so one instance sweeps exactly once. A long-lived writer that
  defers never picks that segment up again itself — recovery needs BOTH a new
  instance AND the segment's date to have passed, so on a long-running daemon
  it can wait indefinitely. Deferring is still right, but the argument has to
  carry more weight than "the sweep will get it": an unsealed segment is
  HONESTLY unsealed and visible through two channels (`onSealFailed` fires at
  deferral time; `verify()` reports it `unsealed`), whereas a seal over a
  prefix is a confident false claim that `sha256sum` cannot reproduce and that
  verification would report `mismatched` on an untampered trail. A
  late-or-absent seal is recoverable; a wrong one is not.
  **X8b3e must merge before X8b3f**, so no reachable code path ever carries
  the window.
- **Four decisions in X8b3f depart from this plan's own PR table (2026-09-12).**
  (1) The writer takes an **injected seal port**, and the owner constructs the
  sealer — the table said the writer would construct it. Constructing it in
  the writer would have meant carrying `maxManifestBytes`, the owner's error
  builder, its failure handler and two retry bounds through options the writer
  has no use for and must not interpret; and because `AppendOnlySealer` has
  `#private` fields it is not structurally fakeable, so without a port there
  is no seam at which "a sealer that throws still leaves the append resolved"
  can be tested at all. (2) The port is **required**, not optional: exactly
  two owners construct the writer and both must seal, so requiring it makes
  "is the sealer wired?" a compile-time fact rather than a test obligation —
  the countermeasure to a never-throws port whose first call site fails no
  test. (3) `onSealFailed` and the **4.8.0 bump land here**, not in X8b4 as
  the table said. This is the slice in which the sealer becomes reachable, so
  it is the first slice in which a seal can fail; shipping it with no
  reporting channel for one slice would be a silent swallow, since `verify()`'s
  `unsealed` verdict is X8b4. No `v4.*` tag exists (ADR-0020, unpublished), so
  X8b4's additions ride the same unreleased 4.8.0. (3b) Wiring the sealer up
  exposed a hole that had been unreachable until then, and X8b3f closes it
  rather than deferring — the same principle that put X8b3d ahead of this
  slice. Because the seal runs AFTER the append, the first-ever append into a
  fresh directory left its own just-created segment on disk before the
  baseline was computed, so `initializeBaseline` wrote
  `upTo: "<today>-0001.jsonl"` where ADR-0102 specifies `upTo: null`. With
  `isAtOrBeforeBaseline` comparing `<=`, that segment was excluded from the
  sweep permanently; and since `discoverActiveSegment` only ever adopts
  today's date prefix, once that date passed nothing would rotate away from it
  either, so the rotation seal could never cover it. **The first segment of
  every trail outliving its first day was permanently unprovable** — the exact
  property the wave exists to deliver. The baseline now excludes the writer's
  own active segment, for the same reason the sweep already does; a
  pre-upgrade trail still classifies its existing segments `legacy`, because
  the exclusion is by name and not a blanket `null`. (4) The seal runs on the
  writer's serialized tail, **outside the promise the caller awaits** — so
  `append()` resolves when the entry is durable, not when the directory is
  quiescent. A manifest write can still land after it. That surfaced within
  the hour as an `ENOTEMPTY` in a suite that removed its directory
  immediately after its last append, and is now documented on both owners'
  public surfaces. It was first treated as a documentation matter and a
  follow-up; **three independent suites then hit it**, the third while
  removing the directory UNDER a live writer — a pattern the writer explicitly
  supports — where the in-flight seal recreated `manifest.jsonl` part-way
  through the removal. A per-suite `ENOTEMPTY` retry is a workaround where a
  seam belongs, so **`flush()` ships here** on both owners rather than in
  X8b4: a point-in-time drain of the writer's serialized chain, never a
  barrier and never an error channel (append failures reach their own caller,
  seal failures reach `onSealFailed`). It is never required for the trail's
  correctness — a process that exits without flushing loses at most a seal,
  which the cold-start sweep recovers.

- **X8b4 is subdivided (2026-09-13, at X8b3f's merge).** As one PR it would
  carry the verification module, the public `verify()`, the reader's gap
  classification and inline digest check, `onArchivedSegment`, and a new
  public error class with its catalog code — a wider shape than X8b3c, which
  measured 70,771 reviewable chars and forced the first split. ADR-0072's
  preference governs again, and the seam here is a dependency order rather
  than a size guess. **X8b4a** ships `M3LAppendOnlyStreamManifestError` and
  `ERR_APPEND_ONLY_STREAM_MANIFEST`, and relocates
  `M3L_APPEND_ONLY_MANIFEST_NAME` to `core/storage/append-only-manifest-types.ts`
  — which together discharge the two findings X8b3f's review acknowledged
  rather than fixed: the sealer's single error builder serving manifest reads
  and manifest appends alike, so the class name discriminates no direction
  and both owners are misnamed in opposite ways; and the `manifest.jsonl`
  literal repeated across nine test files, forced by the `internal/` boundary
  that keeps the constant unreachable. Both later slices depend on it —
  X8b4c throws that class on the archival escalation, and the constant is
  what lets a test outside the package name the sidecar at all. **X8b4b**
  ships `append-only-verify.ts` and the public `verify()`. **X8b4c** wires
  the reader: gap classification ahead of the existing throw, inline digest
  verification, and `onArchivedSegment`. X8b4b lands before X8b4c because
  `verify()` is what an operator reaches for once `read()` has started
  throwing, so it must exist before the throw does.

- **A forged segment name reached a public error's `context` (2026-09-13,
  found during X8b4a).** `M3LAppendOnlyStreamManifestError` is the class this
  slice introduces, and the security pass proved -- by planting two
  disagreeing `seal` lines in a real `manifest.jsonl` and driving built
  `dist/`, not by reading source -- that `admitSeal`'s conflict report carried
  the attacker's own bytes: `context: {"segment":"EVIL-customer-...-<script>"}`,
  identically through both owners, since they share one sealer. The manifest
  ceiling is 8 MiB, so the planted name could be megabytes of arbitrary text.
  The cause was an asymmetry already sitting in
  `append-only-manifest-records.ts` since X8b3b: `ownBaselineUpTo` validates
  `upTo` through `parseSegmentName` and refuses anything it declines, while
  `parseSealRecord` read `segment` with a bare `ownString` and validated
  nothing -- so a name read back off disk was treated as though the writer's
  own counter had produced it. That inverts the sanctioned-name rule, whose
  whole basis is that the library's parser produced the name. Fixed at the
  parse boundary rather than at the reporting site, so every future consumer
  of `ManifestSealRecord.segment` inherits the guarantee; a declined name
  falls into the existing fatal malformed-record path rather than a new one.
  The justification comment at `admitSeal` had asserted the name "derives from
  the writer's clock and counter" -- false for a record read back off disk,
  and left in place it would have talked the next reviewer into re-authorising
  the same pattern. It now names the parse boundary as where the guarantee is
  established, and states plainly what parser-acceptance does NOT prove:
  it constrains the SHAPE, not the provenance.

- **Three prior rounds missed it, and the reason is method, not diligence
  (2026-09-13).** X8b3b, X8b3d and X8b3e all reviewed this module and reasoned
  from the source. The round that found it executed a probe. The same pattern
  produced X8b3e: a proven two-writer rotation window, also found by probing
  built output rather than reading it. Worth stating as a rule for the
  remaining slices -- a claim about what an error's message or `context`
  CONTAINS is verified by constructing the failure and printing it, never by
  tracing the code path. The corollary bit too: X8b4a's own new leak test
  could not fail, because the symlink shape it exercised produces an empty
  `context`, so its `not.toContain(secret)` assertion was green against any
  implementation. A leak test that cannot fail is worse than none, and the
  only thing that exposed it was asking which shapes the assertion could
  actually observe.

- **A seal outranks the baseline in `verify()` (2026-09-13, decided while
  designing X8b4b).** ADR-0102 says "segments at or before the baseline
  classify as `legacy` and are never retro-digested", and read literally that
  makes the baseline the senior classifier. It cannot be, and the reason is an
  attack the manifest's own reader leaves open: `collectRecords` documents
  that "a later `baseline` simply replaces an earlier one", and
  `parseBaselineRecord` refuses only a non-segment-shaped `upTo` and one dated
  later than today. So anyone who can write the directory can append one extra
  `baseline` line naming the newest segment -- a well-formed, present-dated,
  parser-accepted record -- and every genuine `seal` already sitting in the
  same file would be reclassified `legacy` and never checked. A tamper
  detector an attacker silences by appending one line, while the evidence that
  contradicts them sits untouched two lines above, detects nothing. So
  `verify()` classifies on the seal first: a segment the manifest makes a
  claim about is verified against that claim whatever the boundary says, and
  `legacy` means "at or before the boundary AND unsealed". The ADR's sentence
  keeps its intent -- nothing is retro-digested, because a segment with no
  seal is never digested at all. The baseline stays visible as
  `unprovenBefore`, which is what makes the downgrade legible after the fact
  rather than silent. Pin it with a test that plants the later baseline over a
  sealed-and-tampered segment and asserts `mismatched` survives.

- **`verify()` needs a failure channel separate from its verdicts
  (2026-09-13).** The five verdicts say what was found; none of them can say
  "this could not be checked". Folding an `EACCES` on a sealed segment into
  `mismatched` would let a broken filesystem read as tampering -- the same
  conflation `listSegmentFiles` already refuses when it keeps `skipped`
  meaning "not what this writer left behind" rather than "an I/O error
  occurred". So the verification carries `failures` alongside `verdicts`, with
  the invariant that a segment appears in exactly one of the two, never both
  and never neither.

- **X8b4c splits again, and three read-path decisions (2026-09-14, at
  X8b4b's merge).** X8b4c as scoped carried four capabilities -- the manifest
  read on the read path, the sealed-but-absent scan, gap classification, and
  inline digest verification -- estimated at 110-120k reviewable chars. X8b4b
  already spent ADR-0072's "record why" option at 135,593, and a second
  consecutive exception would make the exception the rule. The seam is real
  rather than a size guess: the **escalation** half is independently
  judgeable and is the wave's headline outcome (`read()` detecting whole-date
  archival), while the **digest** half adds content tamper detection and
  depends on the first only for the manifest plumbing. So X8b4c ships the
  escalation and **X8b4d** ships the inline digest check.
  (1) **A manifest that exists and cannot be read is fatal to `read()`.** An
  ABSENT manifest stays contents-free -- a never-sealed trail is legitimate,
  and `readManifest` already draws that line. But a manifest that exists and
  fails (a malformed mid-file line, disagreeing duplicate seals, a
  `formatVersion` above the reader's, `EACCES`) stops the read, because the
  alternative lets one corrupt byte disable archival detection for the whole
  trail -- the "defeated by two `rm`s" shape the X8b4b review already caught
  once on `verify()`'s guidance. The cost is real and is accepted: every
  `read()` then throws while every segment is present and intact, and
  `rebuildHumanActionIndexOnBoot` never throws by contract, so the console
  loses its index rebuild on a corrupt sidecar rather than rebuilding from a
  trail it cannot vouch for. Note the asymmetry this leaves, which is forced
  rather than chosen: deleting the manifest OUTRIGHT is still undetected on
  the read path, because from inside the directory a deleted manifest and a
  never-sealed trail are the same thing. That is this plan's already-recorded
  open item and needs state outside the directory to close.
  (2) **The escalation is eager -- resolved before the first entry is
  yielded.** The absent scan needs only the manifest and the directory
  listing, no segment bytes, so it costs nothing to run up front, and a
  caller with no `onArchivedSegment` handler gets the throw before it has
  consumed anything. This deliberately departs from `onTruncatedTail`, which
  fires in read order; the digest check in X8b4d is unavoidably in-order,
  since a digest completes only at a segment's end, so the two channels will
  differ and both surfaces must say so.
  (3) **Gap classification is an accounting union, not a second code path.**
  `assertNoSequenceGap` walks the segments found on disk; it now walks the
  union of those and the sealed-but-absent ones, so a hole an archived
  segment accounts for is not a gap, and a hole nothing accounts for keeps
  today's `"a segment sequence number is missing"` throw byte-for-byte. The
  union is also what detects a date's deleted LAST segment, which leaves no
  interior gap for the existing walk to see -- the limitation
  `assertNoSequenceGap`'s own TSDoc concedes, and the reason this wave
  exists.

- **X8b4c absorbs the console's archival handler, and X8b4d starts with an
  extraction (2026-09-14, from X8b4c's review round).** Two things the review
  round settled that the next slice inherits. (1) **The console wiring moved
  forward into X8b4c** rather than waiting for X8b5, on the same principle
  that put X8b3d and X8b3e ahead of X8b3f: making `read()` throw on an
  archived date permanently disables `rebuildHumanActionIndexOnBoot`, because
  it never throws by contract, so `insertAll` never runs and every later boot
  re-enters the same path. Worse, its log message asserts "the JSONL trail is
  unaffected ... until the next boot", and both clauses are false for the new
  throw reasons -- an operator would read a permanent audit-integrity finding
  as transient index degradation. Since ADR-0070 _sanctions_ whole-date
  archival, shipping the escalation without the handler would regress the
  console for anyone following the documented procedure. X8b5 keeps the
  `console.md` archive procedure and the `audit-trail-usage.ts` note.
  (2) **`M3LAppendOnlyStream.ts` has 498 bytes of headroom** against
  `check:file-budget`'s 25,000, with no baseline entry, so the hard ceiling
  applies. X8b4d's inline digest verification is a `read()` contract and will
  grow that same doc block, so **the public read/verify TSDoc extraction is
  X8b4d's first move, not a discovery at `pre-push`** -- the gate runs no
  earlier than push, and it already bound twice inside one slice in this wave.
  `append-only-read-wiring.ts` (20 KB free) is the seam to grow the wiring
  half into; the TSDoc half needs its own home.
- **Reviewing a documentation nit found a code defect, and one payload stays
  unhardened (2026-09-14, from X8b4c's third review round).** The bot's
  review returned PASS with no Must-fix: one Should-fix on semver framing and
  two nits. All three were addressed, but the round is worth recording for
  three reasons beyond that. (1) **The Should-fix was right about the framing
  and exposed two factual errors in the PR body**: the version is 4.8.1, not
  the 4.8.0 claimed (#1245 bumped it, not #1229), and "additive minor"
  described the _surface_ while glossing the fact that `read()` now throws for
  a directory that previously read clean -- which is precisely why the
  in-repo caller had to change in the same slice. It is still not a semver
  break, and that was verified rather than argued: no `v4.*` tag, an empty
  `gh release list`, both npm listings empty, and `release.yml` is
  `workflow_dispatch`-only, so no artifact exposes the old behaviour. Note
  CLAUDE.md's "internal, unpublished package" is now a statement about
  _state_, not intent -- #1217 added a real publish workflow -- so the next
  change of this shape will not be free. Whether the wave should land a major
  under ADR-0020's manual-versioning rule is a maintainer call, left open.
  (2) **Reviewing the TSDoc-only nit fix found an unvalidated read.**
  Documenting `collectArchived`'s refusal precedence surfaced that
  `resolveArchivedSegments`' no-handler refusal reported `record.segment` --
  a field nothing in that module validated -- while the validated parse of
  the map key sat unused in the same object. Two reads of "the segment name",
  one checked and one not; the same bug class this repo shipped twice earlier
  in the wave, both times leaking a value into a log. It now reports
  `segmentFileName(parsed.datePrefix, parsed.sequence)`, which is stronger
  than carrying the key: `parseSegmentName` accepts a name only when it
  round-trips through `segmentFileName`, so the reported value is built from
  a calendar-checked ASCII date prefix and a `parseInt` integer _by
  construction_ and cannot carry chosen bytes. That turns the original
  justification -- "rendered entirely from the writer's clock and counter" --
  back into a property of the code, greppable at the call site, rather than a
  promise a comment makes about another module's current strictness. The
  generalizable rule: **a TSDoc round that asserts a safety property deserves
  the same review as a code round**, because the assertion is the artifact
  being shipped. (3) **Recorded, not resolved:** `collectArchived`'s own
  unparsable-seal throw still reports the raw declined name in `context`. It
  cannot be re-rendered -- the name reached that line _because_
  `parseSegmentName` refused it -- so the structural sanction above is
  unavailable there. It is unreachable through the real parser (`ownSealSegment`
  keys the seals map by a field it already made `parseSegmentName` accept, and
  every map reaching the function is that one or the empty absent-manifest
  one), so only an in-memory fixture gets there. Two hardenings were
  considered and declined for this slice: a length cap bounds the size but
  not the _newline_, which is the actual hazard, since a line-delimited
  operator log renders an embedded newline as a second, forged record; and a
  library-computed ordinal carries zero chosen bytes but is nearly useless
  for locating the offending manifest line. **If anything ever relaxes
  `ownSealSegment`, this becomes live and must be revisited before that lands.**
  (4) A process note: the two implementer rounds produced 4.1 KB and 6.3 KB
  of comment for a one-line and a nine-line change, and review cut roughly
  3.5 KB of it as restatement of TSDoc already on neighbouring symbols. Brief
  a spoke to _point_ at an existing argument rather than re-derive it; a
  re-derived rationale is a second copy that drifts.
- **The archive procedure was written from probes, and two of its steps are
  traps (2026-09-14, at X8b4d's merge).** X8b5 documents the operator
  procedure ADR-0102 promised instead of a CLI, as `console.md`'s
  `## Archiving the audit trail`. Every command and every claim in it was run
  against built output first rather than inferred from this plan, which
  changed six things, and a review round found a seventh.
  (1) **`sha256sum -c --ignore-missing` exits `0` when a
  listed file is absent.** Measured, not assumed: with the flag a deleted
  archive copy yields `exit=0` and prints only the surviving lines; without
  it the same directory reports `FAILED open or read` and `exit=1`. The flag
  is exactly what an operator reaches for when the check names files that are
  not there, so it would convert "the archive copy is gone" into a pass --
  the same absence-reads-as-clean conflation this whole wave exists to
  remove. Documented as a do-not, with the failing output quoted so the
  honest failure is recognizable. (2) **The `jq` date filter is
  load-bearing**, and is what makes reaching for that flag tempting. An
  unfiltered `select(.kind == "seal")` lists every date the manifest has ever
  sealed, and in a per-date archive directory every other date's segments are
  legitimately missing -- so the check fails on segments the operator never
  touched. Probed both ways. (3) **`verify()` has no console command, so step
  2 of the procedure is a five-line Node snippet.** That follows from
  ADR-0102's own no-new-CLI decision rather than contradicting it, but it
  means the procedure's one strong pre-flight check is the step least likely
  to be run. Recorded as an honest gap and the snippet printed in full, run
  verbatim against a real trail rather than written from the type signature.
  A `verify` subcommand is the obvious follow-up and is deliberately not
  filed here: it would be the third console surface over the same primitive.
  (4) **`reportAuditTrailUsage`'s `totalBytes` excludes `manifest.jsonl`** --
  `listSegments()` does not recognize the sidecar as a segment, so it never
  enters `segments`, never raises `skipped`, and never enters the total. A
  directory holding three segments totalling 482 bytes plus a 498-byte
  sidecar measured 980 bytes on disk and reported 482. Negligible against
  the 8 MiB segment ceiling, but the sidecar grows by roughly 208 bytes per
  seal and is never rotated, so the gap tracks the segment _count_ rather
  than the trail's size -- and an operator reconciling the report against
  `du` will find it. (5) **The post-archival read shape is pinned by
  observation, not by the read of the code**: with two sealed segments
  removed, `read()` with no handler throws
  `ERR_APPEND_ONLY_STREAM_MANIFEST` carrying
  `{ segment: <the first>, archivedCount: 2 }`, so one name in a log line
  does not imply one missing segment -- which is worth saying out loud in
  operator-facing prose, and now is. With the handler it yields the two
  surviving entries and reports both absent names; `verify()` then reports
  `archived: 2, unsealed: 1` with `unprovenBefore` unchanged at `null`.
  (6) **The console never calls `flush()`, including on shutdown**, which a
  draft of the procedure asserted the opposite of before the claim was
  checked -- `grep flush packages/m3l-console-server/src` finds only HTTP
  backlog accounting. A stop that lands mid-seal loses that seal, and the
  cold-start sweep that recovers it fires from `sealAfterAppend`, whose only
  call site is inside `write()`. So the recovery needs an `append()`, not a
  boot: a console that restarts and records no human action never sweeps, and
  the segment stays `unsealed` -- and therefore un-archivable -- indefinitely.
  Not a defect (the sweep piggybacking the append chain is what keeps the
  healthy path at one manifest read and zero segment re-reads), but it is the
  likeliest way an operator meets an `unsealed` verdict they did not expect,
  so the procedure names it at step 1 instead of leaving it to be discovered.
  Worth generalizing: **two of the first six items are claims a draft of the
  procedure made and a grep or a code read refuted** -- this one, and step
  2's implicit assumption that an operator could simply run `verify()` --
  and both were about a neighbouring module's behaviour rather than about the
  prose being written. The other four are things no draft asserted either way
  and only running the commands surfaced.
  (7) **The one that matters most was found by review, not by probing.** A
  `code-reviewer` pass on the TSDoc flagged that "intra-date deletion
  destroys the trail's readability" overstates the mechanism, and the probe
  that followed settled it: on a four-segment, three-sealed trail, deleting a
  **sealed** segment out of the **middle** of a date and reading with an
  `onArchivedSegment` handler returns the surviving 13 entries and reports
  the absence, while deleting an **unsealed** one throws
  `ERR_APPEND_ONLY_STREAM_READ` **identically with and without the handler**.
  Since ADR-0102 the reader walks the union of on-disk and manifest-sealed
  segments, so the destructive case is keyed on the sidecar, not on position.
  Two sentences this repo had repeated for weeks are therefore wrong --
  "intra-date deletion breaks the trail" and "the sequence check tolerates
  whole-date archival, and only that" -- and `core/storage.md` contradicted
  itself about a hundred lines apart, one paragraph saying a hole an archived
  segment accounts for is not a gap and another saying only whole-date
  archival is tolerated. Corrected at all four live sites by grepping the
  claim rather than the copy in view; ADR-0070's and ADR-0102's instances are
  left as authored, already amended by their own dated Updates.
  `IMPLEMENTATION.md`'s X8b row still carries the old framing and is rewritten
  at close-out. The lesson is not about this claim: **the wave's own
  capability note predicted it** -- this plan has said since X8b1 that sealing
  makes intra-date archival technically safe -- and nobody connected that
  prediction to the prose still asserting the opposite. A capability note that
  says "X becomes safe when this ships" is a standing instruction to grep for
  every sentence claiming X is unsafe, on the day it ships.

### X13. Session → flow export

**Decision:** ADR-0068. Export a session as an ADR-0056 flow definition
using the shared X6/U10 convention; coordinate with U10's state at
execution time.

**Design (2026-09-11 Update on ADR-0068/ADR-0056).** X6 and U10 both
shipped, but the shipped flow format has no inter-step data transport at
all — `M3LCliFlowStep.parameters` is a literal record, and the engine
passes only exit codes and `run-report.json`'s `outcome` between steps.
X13 ships as **snapshot-to-literals**, not live references: each exported
step's `parameters` is the exact `Record<string, string>` the session step
launched with (already persisted on `M3LSessionStepRecord.parameters` —
no re-resolution or store migration needed), and `script` is
`step.operation` verbatim (already the launch-validated script name). A
reference-carrying variant is deferred as **X13a** (Gated, in
`IMPLEMENTATION.md`'s X-series) until the engine itself gains inter-step
data transport.

Concretely:

- `POST /api/v1/sessions/:id/flow-export` (body `{ name, description?,
overwrite? }`) composes the document, screens every parameter name
  (**and its declared aliases**) against the target script's `secret`
  descriptors via the X10a introspection seam, hand-renders YAML
  (every scalar as `JSON.stringify` — a valid YAML 1.2 double-quoted
  scalar for any string, so no quoting-heuristic table is needed), and
  writes `<flows directory>/<name>.yaml` (`wx` by default; `overwrite:
true` to replace). No separate `GET` preview route — the `POST`
  response already returns the rendered YAML.
- Session decision points are not carried (the format has nowhere to put
  one, per this plan's own rejected pause/ask-user option); the response
  reports a `decisionsDropped` count, never prompt/answer content.
- A new `session.flow.export` human-action kind (ADR-0070) needs a
  `console_human_actions.action` `CHECK` migration (SQLite cannot `ALTER`
  a `CHECK`) — landing separately from the route so the file-budget
  extraction it also requires (`audit/record.ts` had 165 bytes of
  headroom) is reviewable on its own.
- The exporter reaches the sessions repository and the script catalog's
  `secret` knowledge through a declared port
  (`M3LSessionScriptCatalogPort`), the same shape `sessions/ports.ts`
  already uses for the run launcher — no `bin/check-eslint-zones.mjs`
  zone change needed.
