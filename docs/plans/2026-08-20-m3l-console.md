## Why this plan exists

The third programme on the shared tracker section: the maintainer named a
full-stack console — button-press script launching, interactive
drill-down (canonically: list SQS queues → dump → pretty JSON → select
field values → DynamoDB query by PK → decide how to proceed), and
comprehensive audit + self-monitoring. A five-facet audit confirmed the
baselines have the right seams and none of the service substrate (no
HTTP server, daemon, registry, streaming, sessions, frontend toolchain,
containers, human-action audit), plus one fleet gap (sqs-etl has no
list-queues) and one design conflict (UI display vs redaction stances)
resolved by ADR-0070's display-vs-persist rule. Eight ADRs record the
decisions; this plan decomposes them into X1–X16.

### X8. Self-telemetry + retention

**Decision:** ADR-0070. Route/script/SSE/policy metrics into the store;
telemetry query endpoints (the UI's monitoring pages); declared
retention policies per artifact class + the operator-run cleanup
command.

**X8b design (ADR-0102; fires the trigger ADR-0070's 2026-09-05 Update
named and its 2026-09-05 second Update gave an owner).** Slice 5a-ii shipped `listSegments()` and a report-only fourth
cleanup section, so the trail's footprint is _observed_ but still
unbounded — and it cannot survive having anything removed from it:
`assertNoSequenceGap` proves contiguity only within one date (so
intra-date deletion makes every later `read()` throw, permanently), while
whole-date deletion passes silently and leaves an archived, a
never-written and a deleted date indistinguishable. X8b ships a
**writer-sealed per-segment manifest**: one directory-wide append-only
`manifest.jsonl` (`M3L_APPEND_ONLY_MANIFEST_NAME`) whose `seal` records
carry each rotated-away segment's `entryCount`, `byteLength` and a plain
sha256 of its raw bytes, so `sha256sum <archived-segment>` re-verifies an
archive with no library involved. A per-segment sidecar is rejected
because it shares the segment's date prefix — the `rm 2026-09-*` ADR-0070
sanctions would delete the proof along with the segment; one
non-date-named file survives the glob by construction. ADR-0070's other
suggestion, a per-entry chained digest, is rejected structurally: it needs
a library-owned field inside the caller's entry, which `read()`'s
verbatim-record contract forbids, and it voids the two-writer
whole-line-interleave guarantee.

Concretely:

- Both owners of `AppendOnlyWriter` get it — `Core.M3LAppendOnlyStream`
  and ADR-0061's `internal/agent/decision-log-writer.ts` — so the
  artifact class does not split. **No new CLI**: archival stays a
  documented manual procedure, and the manifest is what makes it provable.
- A `baseline` record makes backward compatibility bounded _and_ stated:
  segments at or before it classify as `legacy` and are never
  retro-digested, because a digest taken now cannot vouch for bytes a
  pre-upgrade process wrote.
- `read()` verifies **inline and non-optionally** (manifest lookup,
  already-counted `entryCount`/`byteLength`, and sha256 over chunks it
  already reads — CPU only, no extra I/O). `verify()` is the
  `listSegments()`-shaped half: never throws, returns per-segment verdicts
  plus `unprovenBefore`. A sealed-but-absent segment is tolerated only
  when the caller supplies `onArchivedSegment`, mirroring
  `onTruncatedTail` exactly; gap classification moves **ahead** of the
  sequence-gap throw, which is otherwise preserved byte-for-byte.
- A seal is **best-effort and never fatal to the append** — ADR-0061's
  loud-write rule governs the entry, not metadata about already-durable
  bytes. Loudness relocates to bounded retry, a new `onSealFailed`
  handler on both owners, and `verify()`'s `unsealed` verdict.
- A deleted-but-sealed segment now escalates, including a date's own last
  segment and a fully deleted trail — **new** tamper detection, not a
  relaxation. Intra-date archival becomes technically safe and stays an
  explicit non-goal (custody of the archive is unaddressed): capability
  unlocked, permission withheld, filed as its own row.
- `check:file-budget` is the binding constraint, so the reader cannot
  absorb the verification wiring: a pure-move `refactor:` slice extracts
  `append-only-fs.ts` and `append-only-lines.ts` first. Slices X8b3\* and
  X8b4 stay separate because `perFile: true` coverage binds each new `src`
  file to the tests that exercise it, and retrofitting that split later is
  structurally impossible.
- **Correction (2026-09-12, after X8b2 shipped).** The planning note above
  originally added that an `internal/`-only slice would ship `src/` with
  zero coverage, because "tests exercise only the public barrel" — and used
  that to argue X8b3 could not be subdivided. That is false in this repo.
  `append-only-fs.ts` and `append-only-lines.ts` both landed in X8b2 as
  `internal/` modules reached by no barrel, each with its own direct test
  suite at 100% branch coverage, and `append-only-digest.ts` did the same in
  X8b3a. With that constraint gone, ADR-0072's preference governs instead:
  X8b3 is subdivided into **X8b3a/b/c** because as one PR it measured
  ~133,000 reviewable chars against `check:review-size`'s 75,000 soft
  target, and each part is independently reviewable.
- **Split again (2026-09-12, at X8b3c's push).** The sealer alone measured
  70,771 reviewable chars; the writer wiring X8b3c was to carry with it
  would have taken the slice past 100,000. That wiring is now its own slice
  — the same principle that produced a/b/c, applied to a measurement that
  did not exist when the a/b/c split was decided.
- **A hardening slice is inserted ahead of the wiring (2026-09-12).** A
  security review of X8b3c executed probes against built output and defeated
  the tamper-evidence property four ways: a seal pre-planted in the manifest
  before the genuine one suppresses it silently (the conflict refusal fires
  only when two claims coexist, and a forgery written first is never
  contradicted); a calendar-invalid name such as `9999-99-99-9999.jsonl`
  becomes the write-once baseline and classifies every segment `legacy`,
  killing the sweep permanently; sixty-four `0000-00-00-NNNN.jsonl` decoys
  consume the whole sweep budget; and a forward clock step makes the sweep
  digest a segment another writer is still appending to, which the module
  itself calls the worst failure this design can produce. The first three
  need an attacker who can write into the trail directory — the envelope
  ADR-0102 concedes for manifest DELETION — but they differ in kind from
  what it conceded: deletion downgrades a trail visibly, while these
  manufacture a confident verdict about bytes an attacker chose. The clock
  step needs no attacker at all. **X8b3d must merge before X8b3f**, so no
  reachable code path ever carries these windows — nothing constructs the
  sealer until the wiring lands.
- **The threat model X8b3d leaves behind (2026-09-12).** Recorded here rather
  than as an ADR-0102 Update: `docs/adr/README.md` permits an Update only
  where it executes a revisit trigger the accepted Decision already declared,
  and 0102 declared none for this. The decision itself is unchanged — what
  changed is that the code now delivers what it claimed.
  **Closed:** a `baseline.upTo` that names no segment is refused at the
  manifest's own validation boundary, so a forged baseline is a loud fatal
  read rather than a silent policy change; a baseline is never derived from a
  future-dated segment; `parseSegmentName` refuses a date that is not a real
  calendar date, which removes both the `9999-99-99` baseline poison and the
  `0000-00-00` sweep decoys; and a rotation seal now MEASURES a segment the
  manifest already names instead of skipping it, so a seal pre-planted before
  the genuine one is contradicted rather than silently honoured.
  **Narrowed, not closed:** a digest refuses a measurement of a file that grew
  during the read, which catches the common case of a clock step inducing a
  sweep of a live segment — but an append landing after the post-read stat
  still yields a seal of a prefix. The structural fix belongs to X8b3f, where
  the writer can tell the sealer never to digest its own active segment; the
  residual cross-process case is a clock-trust limitation, not a code defect.
  **Open by design:** the SWEEP still trusts the manifest as a membership
  test, so a forgery pre-planted against a segment that is swept rather than
  rotated stays undetected until `verify()` ships in X8b4. Corroborating a
  whole backlog on every cold start would turn one start-up into an unbounded
  read of the trail, which is what the sweep's budget exists to prevent.
- **A second hardening slice is inserted ahead of the wiring (2026-09-13).** A
  security review of the completed-but-unmerged wiring executed probes against
  built output and proved a window nothing had covered: the sweep's
  `datePrefix < today` rule guarantees no conforming writer can still be on a
  segment, but the ROTATION seal has no equivalent guard. With two
  `M3LAppendOnlyStream` instances over one directory — a configuration the
  class's own TSDoc advertises as supported, since `O_APPEND` makes concurrent
  writers interleave whole lines — each adopts the active segment at its real
  size and then counts only its OWN bytes. Writer A's local counter crosses
  `maxSegmentBytes`, so A rotates off the segment and seals it while writer B
  is still appending to it. The manifest then permanently claims a digest over
  a PREFIX: `sha256sum` of the archived segment cannot reproduce it, so that
  date's archival is unprovable, and X8b4's inline `read()` verification would
  classify an untampered trail `mismatched` — the false-positive-on-a-tamper-guard
  this design calls its worst failure. No amount of re-`stat`-ing at digest
  time closes it, because neither writer can see the other's bytes.
  **X8b3e closes it with evidence the rotating writer already holds.** A
  rotation now carries the byte count the writer believed the segment held;
  if the file measures larger, someone else appended, and the seal DEFERS
  rather than claims. That needs no cross-process coordination — which
  ADR-0102 deliberately does not have.
  **What deferring costs, stated correctly — the PR review caught this
  overclaim.** A first draft of this bullet said a deferred seal arrives "a
  day late, via the sweep". False: the sweep is per-INSTANCE, not per-day.
  `#sealAndSweep` flips `#swept` on its first call and returns early on every
  later one, so one instance sweeps exactly once. A long-lived writer that
  defers never picks that segment up again itself — recovery needs BOTH a new
  instance AND the segment's date to have passed, so on a long-running daemon
  it can wait indefinitely. Deferring is still right, but the argument has to
  carry more weight than "the sweep will get it": an unsealed segment is
  HONESTLY unsealed and visible through two channels (`onSealFailed` fires at
  deferral time; `verify()` reports it `unsealed`), whereas a seal over a
  prefix is a confident false claim that `sha256sum` cannot reproduce and that
  verification would report `mismatched` on an untampered trail. A
  late-or-absent seal is recoverable; a wrong one is not.
  **X8b3e must merge before X8b3f**, so no reachable code path ever carries
  the window.

### X13. Session → flow export

**Decision:** ADR-0068. Export a session as an ADR-0056 flow definition
using the shared X6/U10 convention; coordinate with U10's state at
execution time.

**Design (2026-09-11 Update on ADR-0068/ADR-0056).** X6 and U10 both
shipped, but the shipped flow format has no inter-step data transport at
all — `M3LCliFlowStep.parameters` is a literal record, and the engine
passes only exit codes and `run-report.json`'s `outcome` between steps.
X13 ships as **snapshot-to-literals**, not live references: each exported
step's `parameters` is the exact `Record<string, string>` the session step
launched with (already persisted on `M3LSessionStepRecord.parameters` —
no re-resolution or store migration needed), and `script` is
`step.operation` verbatim (already the launch-validated script name). A
reference-carrying variant is deferred as **X13a** (Gated, in
`IMPLEMENTATION.md`'s X-series) until the engine itself gains inter-step
data transport.

Concretely:

- `POST /api/v1/sessions/:id/flow-export` (body `{ name, description?,
overwrite? }`) composes the document, screens every parameter name
  (**and its declared aliases**) against the target script's `secret`
  descriptors via the X10a introspection seam, hand-renders YAML
  (every scalar as `JSON.stringify` — a valid YAML 1.2 double-quoted
  scalar for any string, so no quoting-heuristic table is needed), and
  writes `<flows directory>/<name>.yaml` (`wx` by default; `overwrite:
true` to replace). No separate `GET` preview route — the `POST`
  response already returns the rendered YAML.
- Session decision points are not carried (the format has nowhere to put
  one, per this plan's own rejected pause/ask-user option); the response
  reports a `decisionsDropped` count, never prompt/answer content.
- A new `session.flow.export` human-action kind (ADR-0070) needs a
  `console_human_actions.action` `CHECK` migration (SQLite cannot `ALTER`
  a `CHECK`) — landing separately from the route so the file-budget
  extraction it also requires (`audit/record.ts` had 165 bytes of
  headroom) is reviewable on its own.
- The exporter reaches the sessions repository and the script catalog's
  `secret` knowledge through a declared port
  (`M3LSessionScriptCatalogPort`), the same shape `sessions/ports.ts`
  already uses for the run launcher — no `bin/check-eslint-zones.mjs`
  zone change needed.

- X1 (docs wave): `pnpm verify` green; tracker/hub-key gates clean;
  doc-count/index/provenance gates no-ops; `pnpm sync:hub` dry-run
  reviewed, applied post-merge.
- Code rows: the standard battery (`typecheck`, `lint`, `test:coverage`
  thresholds, `build`, `check:zones` with no zone widened beyond the
  new console zones' own additions, `check:api`/`check:exports`
