# Work log — F23 field test against PR #523 / issue #474 (2026-08-21)

F23 (#571) shipped ADR-0072 and its tooling — `pnpm check:review-size`,
`pnpm check:file-budget`, the `check:test-counts` sibling fix, and
`check:scaffold-seam`'s `## Landing plan` enforcement — across three merged
PRs (#572, #573, #574). Every claim ADR-0072 makes about what those gates
would have caught on PR #523 (`core/procedure`, tracker item **B2**, issue
**#474**) was, until this pass, untested: the discipline was written _from_
the post-mortem, never run _against_ the branch that produced it.

This report runs the shipped gates against `origin/feat/core-procedure-engine`
(`1684192`), derives a concrete landing-plan candidate for B2 from the
measurements, and gives an honest assessment of whether the discipline
addresses the failure that actually happened. Issue #474 remains open; this
does not re-land B2, it gives the next attempt a validated starting point.

## Method

A disposable detached worktree was created at
`origin/feat/core-procedure-engine`, with `bin/` and `package.json` checked
out from `origin/main` grafted in (the F23 gates postdate that branch and
don't exist on it natively):

```bash
git worktree add --detach <scratch>/b2-field-test origin/feat/core-procedure-engine
git -C <scratch>/b2-field-test checkout origin/main -- bin/ package.json
```

Each gate below ran inside that worktree against the real B2 tree. Output is
reproduced verbatim except where noted.

**Verdict: fires, correctly.** This reproduces the CI rejection locally, for

CI measured a slightly different point in the branch's history (a later
commit, or a difference in `gh pr diff`'s unified-vs-triple-dot range) than
`git diff <merge-base>..<branch-tip>` used here. The delta is immaterial to
every conclusion below — both numbers are ~1.7x the 300,000 ceiling.

**Verdict: fires, and finds one thing the plan didn't predict.** The four src

ratchet working exactly as designed against a real branch that touches

### `check:scaffold-seam`

As shipped, this branch's `docs/implementation-status.md` already marks
`procedure` ✅ (the finished, merged state) — so the gate is vacuously green,
as it is for every completed module today. To exercise the actual enforcement

```text
✗  docs/reference/core/procedure.md is missing a "## Landing plan" heading —
   required while status is not yet ✅ (ADR-0072)
```

**Verdict: fires correctly** in the state it's designed for. This confirms
the gate's vacuous-green-today, bites-on-the-next-in-flight-module design
works as intended, using B2 as the concrete in-flight case it was written for.

### `check:test-counts`

**Verdict: fires correctly.** `procedure` (the primary, basename-matching
file) reconciles against the recorded `58`; the three sibling files are
surfaced by `findUncountedFiles` exactly as the fix intends — this is the
literal drift the post-mortem named as motivating the fix, reproduced against
the real data. (The much longer `mismatches` list `diffCounts` also produced
is an artifact of feeding only these four files' synthetic counts against the

### Where the size actually comes from

Four files are structurally oversized, and they are the same four
`check:file-budget` flags. Their internal structure — read directly, not
inferred from names — gives real seams, not guesses:

**`M3LProcedure.ts`** (1,731 lines, one class, ~35 private methods) is
already the _thin_ half of the design — `internal/procedure/` externalizes
much of the algorithmic work (`resolve.ts`, `graph.ts`, `evaluate.ts`,
`trace.ts`, `context.ts`, `digest.ts`, `equality.ts`, `definition.ts`,
`errors.ts`) as free functions the class delegates to. The class itself still
carries four cohesive method clusters that were never externalized:

- run-entry + option validation (`run`, `#validateRunOptions`,
  `#validateMaxIterations`, `#validateParameters`, `#validateProgressOptions`)
- phase-one orchestration (`#runValidated`, `#runRemainingPhases`,
  `#finishEarlyPhaseOne`, `#checkAbortBeforePhase`, `#finishOutcome`,
  `#runPhaseOne`)
- step advancement (`#advanceOneStep` through `#checkIterationCeiling` — the
  largest cluster, ~373 of the file's 1,731 lines)
- step execution/recovery and conclusion (`#executeOneStep` through
  `#buildTelemetry`)

Extracting the latter three clusters into new `internal/procedure/` modules
(mirroring the pattern already used for every other algorithmic concern in
this submodule) leaves a thin orchestrator class of roughly 6,000–7,000 bytes
— comfortably under the 25,000-byte ceiling — with the extracted logic split
across two or three new internal files, each independently under ceiling.

**`types.ts`** (849 lines) already has clean, pre-existing section dividers:
values/scalars, references, steps, records/context, conditions, cases, build
options, run/progress options, outcomes. Splitting along those boundaries
(e.g. `types/values.ts`, `types/steps.ts`, `types/conditions.ts`,
`types/run.ts`, re-exported from `core/procedure/types.ts` or an index) is
mechanical — no logic changes, only declaration regrouping — and each
resulting file is well under 10,000 bytes.

**`validate.ts`** (1,217 lines) has the same property: step/case/fallback
_normalization_ functions form one cohesive block; duplicate-id, cycle,
invalid-jump-target, and duplicate-priority _checks_ form a second; the
regex-quantifier pattern-scanning helpers (`isQuantifierChar`,
`advancePatternScan`, `hasQuantifiedGroup` — the code exercised by R5's
unbounded-recursion defect) form a third, small, self-contained one. Three
files, each comfortably under ceiling.

**`procedure-guards.test.ts`** (81,143 bytes) is documented in the branch's
own Notes column as covering three concerns at once — "guards/tracing/
adversarial" — and was never split along that seam despite the seam already
being named in prose before the file was written.

**This confirms the plan's central hypothesis.** ADR-0072 called a
retrofitted split "structurally impossible" while treating `M3LProcedure.ts`
as a fixed 63,988-byte unit whose test coverage bound it to
`procedure-guards.test.ts`. That framing was correct for the _file as shipped_
but overstated the _submodule_: `check:file-budget` independently rejects
that file at 2.5x its ceiling, and decomposing it along the seams above is
exactly the kind of internal-module extraction this submodule was already
using everywhere else. The decomposition breaks the `createProcedureBuilder`
binding that made a whole-class split impossible, because the extracted
pieces no longer need to share one class's private state.

**Caveat, stated plainly:** the byte figures for the _proposed_ decomposed
files above are estimates derived from proportional line counts, not measured
output — nobody has written this decomposition. Confirming it holds requires
actually authoring it and re-running `check:file-budget` and, critically, the
per-file `perFile: true` coverage thresholds (90% lines / 83% functions / 80%
branches / 89% statements) against each resulting file — that verification is
carried forward as an open step in the landing plan, not asserted here as
fact.

**Honest conclusion for Phase 2:** slice 1 is measured and genuinely
compliant today. Slices 2 and 3 are **not** compliant as currently
partitioned — slice 2 is 1.9x the soft target and slice 3 is 3.6x, even before
counting the src-side decomposition's own byte cost. Reaching compliance for
the engine (slice 3) requires the file-level decomposition to actually happen
first, and even then the two oversized test files (`procedure-guards.test.ts`
83,632 bytes, `procedure.test.ts` 57,886 bytes) need their own split before
slice 3 can land as one PR — most likely 2–3 further slices along the
run-loop/advancement/conclusion boundaries identified above. **A compliant
slicing exists in outline, is not fully specified by this pass, and requires
implementation work — file-level decomposition plus test-file resplitting —
before it can be executed.** This is weaker than "yes, here is the plan" and
stronger than ADR-0072's "structurally impossible"; the honest middle is what
the measurements support.

## Phase 3 — Does F23 address the failure that actually happened?

The post-mortem's own conclusion was **non-convergence, not size**: five
review rounds kept finding new instances of one defect class (unguarded reads
of caller-supplied values at the public boundary), and R4 found that the fix
for R3 had _reintroduced_ a hazard already removed on that same module.

**Would smaller PRs have converged?**

- **R1** (13 must-fixes from a six-spoke review) spans the whole submodule —
  `outcome.trace` (engine/conclusion), `ERR_PROCEDURE_UNDECLARED_JUMP`
  (types + validate + engine), forgeable built definitions (builder), the
  caller graph read twice (graph.ts/resolve.ts). Slicing would have caught
  this in pieces across slices 1–3 rather than all at once — a genuine win:
  a defect found in slice 1 doesn't block or discard slices 2–3's unrelated
  work.
- **R2** (the `loop`+`continueOnFailure`/`jumpsTo` interaction) lands
  specifically in the step-advancement cluster (slice 3) and the `steps`
  section of `types.ts` (slice 2) — a cross-slice defect. Splitting the
  submodule does not eliminate cross-slice defect classes; it just changes
  which PR discovers them.
- **R3/R4** (the builder validation gap, and the fix for it reintroducing a
  validate-then-re-read hazard) both land in slice 2 (`M3LProcedureBuilder.ts`
  - `validate.ts`). **This is the critical case**: R4 shows the same reviewer
    finding the _same class of defect twice_ on the _same module_, because the
    first fix's own review didn't check for reintroduction of a class already
    fixed elsewhere in the repo. Slicing does not touch this failure mode at
    all — a smaller slice 2 would still need the same two review rounds to
    reach the same fix, because the defect class recurs regardless of diff
    size. The one candidate mitigation F23 shipped is
    `.claude/rules/library-src.md`'s generalized "every caller-supplied value
    crossing the public boundary is validated once, at the boundary" bullet —
    a rule a reviewer or implementer can check against directly, rather than
    rediscovering per round. It is a partial answer: it makes the defect class
    _checkable_, not _impossible_.
- **R5** (unbounded recursion over caller `run()` parameters) and the
  follow-up audit's three further sites are all instances of the same
  boundary-validation class R3/R4 already exposed — the same conclusion
  applies.

**What F23 genuinely fixes, independent of convergence:** the discarded-work
cost. #523 discarded 26 commits when it was abandoned. A sliced landing where
slice 1 passes review and merges before slice 2 exists banks that work — a
failed review round on slice 3 no longer threatens slices 1–2. This is a real
structural improvement, separate from and weaker than "the review process
converges faster."

**What F23 does not touch:** the root cause of R4 specifically — a review
process that re-approved a fix without checking it against defect classes
already fixed on the same module — is a review-memory gap, not a size gap.
Smaller PRs make each individual review faster and lower-stakes, but nothing
shipped in F23 makes a reviewer (human or spoke) less likely to miss a
reintroduced hazard. The `library-src.md` rule addition is the only shipped
artifact that even partially reaches this, and it is advisory prose a
reviewer must apply, not an enforced gate the way `check:file-budget` is.

**Conclusion: F23's size/process gates work exactly as designed and are
independently valuable — they reproduce the CI rejection locally, catch a
ratchet violation the plan didn't anticipate, and enforce the landing-plan
heading correctly. They do not solve non-convergence, and the ADR does not
claim they do, but the tracker's own framing ("this item exists so that
cannot recur") slightly overstates the coverage: a sliced B2 re-attempt could
still hit a multi-round R3/R4-style loop within any single slice.** The size
discipline and the convergence problem are different problems; F23 solved the
first and partially mitigated the second via one rule addition.

## Gaps found

Three tooling gaps surfaced while running this field test. None block B2's
re-landing; all are recorded as follow-up items (see
`docs/plans/IMPLEMENTATION.md`).

1. **`check:review-size --json` has no per-file breakdown.** The CLI's `--json`
   output exposes only the aggregate `reviewableBytes` and a prose top-5 list;
   planning a split (as Phase 2 above required) needs the full per-file table,
   which today is only reachable by importing the script's internal
   `splitDiffByFile`/`filterForReview` exports directly, as this report did.
   A `--files` flag or a `perFile` array in `--json` output would make this a
   one-command operation instead of a throwaway script.
2. **`pnpm worktree:new` cannot check out an existing ref.** It always
   branches fresh from `origin/main` (`bin/worktree-new.mjs`); auditing an
   abandoned branch required falling back to raw `git worktree add --detach`.
   Not a defect — the tool is doing what ADR-0013 designed it for — but a
   `--from <ref>` option would make this kind of investigation a supported
   workflow rather than a manual git dance.
3. **`check:file-budget` has no `--base`/`--head`.** Unlike
   `check:review-size`, it only scans the working tree, so pointing it at a
   branch requires a worktree (as this report did) rather than a direct
   invocation. Given the ratchet is inherently a working-tree-state check
   (it compares against a committed baseline file, not a diff range), this
   may be working as intended — noted for the tracker to weigh rather than
   resolved here.
