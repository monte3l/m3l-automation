## What didn't go as planned, and why

Everything executed as planned; no divergences were observed. This is the
expected shape for a close-out PR that only records a decision already
implemented and verified across the prior two PRs — the substantive risk in
this 3-PR sequence lived in PR 1 (the parser generalization) and PR 2 (the
new gate + its docs backfill, where a real ROADMAP/IMPLEMENTATION tracker
drift was caught mid-task), both already logged separately.

## Lessons learned

- **A close-out PR's own review risk is proportional to how much of the
  substance it actually implements, not how many files it touches.** This
  PR touched seven files across three skills, an ADR, a tracker row, and a
  cross-reference doc, but every one of those edits was _recording_ a
  decision the prior two PRs had already implemented and tested — there was
  no new logic to get wrong, which is exactly why the review came back
  clean. Don't read "clean review" as evidence the earlier, code-bearing
  PRs in a sequence carry the same low risk; they don't, and shouldn't be
  judged by this PR's smooth landing.
- **`gh pr checks`'s `skipping` bucket is not a failure to investigate on a
  docs-only PR** — it's the expected outcome of this repo's own
  path-conditional CI jobs correctly recognizing there's no `src/`/`tests/`
  diff to build, test, or lint. Confirm via `gh pr view --json
mergeable,mergeStateStatus` (`MERGEABLE`, not blocked) rather than chasing
  every `skipping` row as if it were `pending`.
- **A tracker-row PR-number placeholder (`#NNNN`) is resolved in its own
  tiny follow-up commit, not guessed at authoring time.** This repo already
  had the convention (T9's row); the discipline is knowing the real number
  only exists once `gh pr create` returns it, and treating that as a small,
  expected, separate commit rather than something to predict or avoid.
- **`pnpm sync:hub -- --apply` can close more than the row you flipped** — a
  governance epic with no remaining open children closes alongside its last
  item, in the same run. This is intended sync behavior (the epic literally
  has nothing left to parent), not a sign something went wrong; verify it
  by reading the dry-run's stated reason (`"not planned: Item removed from
source trackers"`) rather than treating an unexpected second closure as a
  bug.
