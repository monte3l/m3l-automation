# Work log — `aws/eks` submodule (2026-07-27)

This log covers implementing the `aws/eks` operations wrapper — the first PR
of the two-PR chain unblocking the `eks-ops` consumer script (roadmap W4). It
ran through the full `starting-work` → `scaffolding-submodules` →
`implementing-submodules` → `syncing-docs` pipeline: what shipped, what
matched the plan, one real divergence (a confirmed security finding), and the
durable lessons. The plan was authored and approved in plan mode as a
session-local plan file (outside this repo's tracked tree, per this
environment's plan-mode convention), so there is no in-repo path to link.

## Summary

Shipped `M3LEKSOperations`: 12 EKS control-plane operations (list/describe/
create/update-config/update-version/delete for both clusters and nodegroups)
plus 4 `waitUntil*` lifecycle waiters — 21 plain/options types, `M3LEKSOperationError`.
Confirmed against the installed `@aws-sdk/client-eks@3.1079.0` directly (not
assumed): no merged `UpdateCluster`/`UpdateNodegroup` command; the four
`update*` operations are asynchronous and resolve an `M3LEKSUpdate` tracking
object, not the mutated resource; `ListClusters`/`ListNodegroups` return
names, not ARNs; `describeCluster`/`describeNodegroup` resolve `undefined` on
`ResourceNotFoundException` (`listNodegroups` does not — it throws like any
other failure); the `*Active`/`*Deleted` waiters' RETRY-vs-FAILURE acceptor is
asymmetric between cluster and nodegroup, verified against the real generated
waiter source rather than the SDK's prose docs.

## What didn't go as planned, and why

### 1. The waiter TIMEOUT/ABORTED path leaked a cluster-registration secret; the doc's own prior claim that this was "safe" was wrong

The pre-implementation doc draft classified the waiter FAILURE path as a
confirmed secret-leak channel (the SDK embeds the full last `DescribeCluster`/
`DescribeNodegroup` response into the raw error) but explicitly called the
TIMEOUT/ABORTED path "safe in the common case," reasoning that
`checkExceptions` overwrites `reason` with a short literal string. The
implementation followed that draft and forwarded `error.message` verbatim on
both paths.

The post-implementation security review disproved the "safe" claim by
**executing** the real `@aws-sdk/client-eks@3.1079.0` waiter machinery against
a fixture carrying a planted secret, rather than reasoning from the SDK
source alone: `@smithy/core`'s `createMessageFromResponse` only produces a
short key when `$metadata.httpStatusCode` is present on the observed
response; a `$responseBodyText` deserialization-failure branch — reachable
independent of `$metadata` presence — serializes the entire response into the
timeout/abort error's message instead, including `connectorConfig.activationCode`.
Fixed by returning a fresh, static, library-constructed `reason` string on
both the TIMEOUT/ABORTED and FAILURE paths, built only from the resource
name/cluster name already available to the caller — never from the raw SDK
error. Both the affected source (`client.ts`) and the 8 tests that had
asserted the old forwarded-message behavior were updated in the same fix
round.

**Why it happened:** Reading the SDK's type declarations and even its
generated JS source is necessary but not sufficient to characterize what a
runtime error's message actually contains — `checkExceptions`'s "the common
case is safe" reasoning was plausible from the code path most likely to
execute, but missed a less-obvious branch (`$responseBodyText`) that fires
independently of the condition (`$metadata` presence) the doc reasoned about.

**Fix for future:** For any claim about what data flows through an SDK
error's `message`/`cause` on a failure path, prefer executing the real
SDK/waiter machinery against a fixture carrying a planted secret over
reasoning from source alone — a `console.log`/assertion against the actual
runtime output is the only way to catch a branch the source-reading pass
missed. This is the same lesson `aws/cloudformation`'s waiter doc already
surfaced once (a `FAILURE` terminal state's embedded response being visible
via `cause`) — the recurrence here (a _second_, narrower leaking branch on a
path the doc had already investigated and pronounced safe) suggests dispatching
the security review's execution-based verification _before_ finalizing any
waiter-related "safe" claim in a submodule's spec, not only after
implementation.

## Lessons learned

- **Execute, don't just read, when characterizing what an SDK error's message
  contains.** Reading generated waiter source is necessary to find the
  code path but is not sufficient to prove a claim like "the common case is
  safe" — a fixture carrying a planted secret, run through the real SDK, is
  the only check that catches a branch (like `$responseBodyText`) a
  source-reading pass reasoned past. _(promoted → `.claude/rules/library-src.md`)_
- **A pre-RED contract-extraction pass against the real installed SDK is
  worth dispatching even when the hub has already manually verified several
  claims.** The hub's own manual SDK reading during scaffolding (confirming
  the async `update*`/`M3LEKSUpdate` shape, the asymmetric FAILURE-status
  waiter sets) still left six further corrections for the dedicated
  `spec-conformance-reviewer` pass to find — independent verification finds
  gaps self-verification misses, even when the self-verification was itself
  SDK-source-grounded rather than assumed.
- **Branch-coverage gaps in AWS wrappers cluster in one predictable place:
  optional-field mappers whose fixtures are always "full."**
  _(promoted → .claude/agents/test-author.md)_ Every prior
  wrapper (`ecs`, `codepipeline`, `cloudformation`) likely hit the same
  pattern; a handful of "minimal fixture" tests (bare-required-fields-only,
  both request and response side) closes most of the gap in one pass rather
  than one test per field.
- **A doc's own "safe in the common case" carve-out is a claim to
  re-verify at implementation time, not inherit as settled.** The doc that
  investigated a security-shaped question and drew a boundary around what's
  safe should be treated as provisional until the security review's
  execution-based check confirms it — not as a closed question the
  implementer can build on unquestioned.
