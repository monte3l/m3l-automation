## What didn't go as planned, and why

### 1. PR 1's plan called for a `cache-dependency-path` fix that never actually landed in PR 1

The PR 1 plan's "CI store cache — fix it permanently, not once" section
specified adding `cache-dependency-path` to
`.github/actions/setup/action.yml` as part of PR 1, so that PR 2's bump
would get a clean cache miss. Checking the live file at the start of PR 2
showed it was never added — PR 1 shipped the consistency gate but not this
adjacent cache fix from the same plan section.

**Why it happened:** The gap wasn't caught by any gate (there's no
mechanical check tying a plan file's stated scope to what a PR actually
ships) or by the PR 1 pre-push/post-push review passes, since neither
reviewer had the plan text to cross-check against — they review the diff on
its own merits.

**Fix for future:** When resuming a multi-PR plan sequence after a
compaction or a gap in time, re-diff the plan's stated scope for the
_just-completed_ PR against what actually landed, not just against what's
left to do — a plan can under-deliver on an earlier step silently. Caught
here only because PR 2 happened to depend on the same fix and needed to
re-derive it from scratch.

### 2. GitHub auto-merge fired on PR #1185 before its Should-fix findings could be folded in

`claude-pr-review.yml` posted a PASS verdict on #1185 with two Should-fix
findings (missing `cache-dependency-path` on two workflows outside the
composite action; a test-coverage gap for the pin probe's non-exact
branch). Per `resolving-pr-comments`, a PASS-with-Should-fix should
continue into the fix/verify/commit loop within the same PR — but
`should-fix-ack` isn't yet in this repo's enforced GitHub required-checks
list (confirmed: only `Dependency Review`, `CodeQL`, and `verify` are
enforced), so the armed auto-merge fired the moment `verify` went green,
merging #1185 while the fix pass was still in flight (a `test-author`
dispatch for the coverage gap was mid-run).

**Why it happened:** `should-fix-ack` (ADR-0097) is a required-check-_in-waiting_
by design — CLAUDE.md's own commands table lists it as a `pre-push` lane
item, but nothing in this sequence's earlier research confirmed whether
GitHub's branch-protection required-checks list had actually been updated
to include it yet. It hadn't. `creating-prs`' own documented risk
("auto-merge fires the moment the required checks pass... every finding
becomes a follow-up PR") predicted this exact race but the risk wasn't
re-checked against live branch-protection settings before arming
auto-merge on a PR with foreseeable Should-fix findings.

**Fix for future:** Before arming `gh pr merge --auto` on a PR expected to
carry Should-fix findings (i.e., any bot-reviewed PR), check
`gh api repos/{owner}/{repo}/rulesets` or the branch-protection settings
directly for whether `should-fix-ack` is actually in the required list —
don't assume ADR-0097's existence means the enforcement mechanism is fully
wired. If it isn't required yet, either hold off on auto-merge until the
bot review posts, or budget for a same-day follow-up PR as the fallback
(which is what happened here, cleanly, but cost an extra PR/review/merge
cycle that a held auto-merge would have avoided).

### 3. The re-checkout to a new branch after the merge race needed a small manual maneuver, not a documented recovery step

Once #1185 merged mid-fix-pass, the local worktree's branch
(`feat/pnpm-12-bump`) was now squash-merged and stale. The uncommitted
Should-fix fixes (two workflow edits plus the in-progress test file) had to
be carried onto a _new_ branch built off the just-updated `origin/main`
(`git checkout -b fix/pnpm-12-should-fix origin/main`) rather than pushed
to the now-dead branch. This worked cleanly because the new branch's base
already contained everything the stale branch had, and the uncommitted
diff was on top of unchanged content in the shared area — but that's a
lucky property of this specific edit sequence, not something the recovery
path guarantees in general.

**Why it happened:** Neither `resolving-pr-comments` nor `creating-prs`
documents the exact git maneuver for "the branch I'm fixing was merged out
from under me mid-fix-pass" — the "every finding becomes a follow-up PR"
guidance names the _outcome_ but not the _mechanics_ of getting there when
uncommitted work already exists in the old branch's worktree.

**Fix for future:** `resolving-pr-comments` or `creating-prs` should
document this maneuver explicitly: `git fetch origin main`, confirm the
merge landed (`git log <old-branch> ^origin/main` should be empty of
_content_ even though the commit itself won't be an ancestor post-squash),
then `git checkout -b <new-branch> origin/main` to carry uncommitted
changes onto a live base before committing and pushing as a fresh PR.

## Insights

- **A multi-PR plan's per-PR scope needs re-verification against the live
  repo at the start of each subsequent PR, not just at the start of the
  first.** PR 1's plan section for the CI cache fix silently didn't ship;
  it was only caught because PR 2 needed the same fix and re-derived it
  from the live file instead of trusting the plan's "already done" framing.
  _(See "What didn't go as planned" #1.)_
- **`should-fix-ack` being declared in CLAUDE.md's commands table is not
  the same as it being an enforced GitHub required check** — check the
  live branch-protection/ruleset config before arming auto-merge on a PR
  where a Should-fix finding is plausible, not just the repo's own
  documentation of intended enforcement.
- **The git recovery maneuver for "my branch merged mid-fix-pass" is
  `git checkout -b <new-branch> origin/main` from inside the stale
  worktree/branch with uncommitted changes still present** — carries the
  uncommitted diff onto a live base cleanly when the new base already
  contains everything the old branch had. Worth promoting into
  `resolving-pr-comments` as an explicit documented step, since the skill
  already anticipates the _outcome_ (a follow-up PR) but not this mechanic.
- **Reaching an unexported `bin/lib/` probe function for direct test
  coverage through its owning table's exported field (`ADR_CLAIMS.find(c
=> c.id === ...).probe`) is a clean pattern** — it satisfies a
  coverage-gap Should-fix without breaking the file's deliberate
  no-per-probe-export convention. Generalizes to any descriptor-table
  module (`bin/lib/integration-stance.mjs`'s `INTEGRATION_DESCRIPTORS`
  follows the identical shape) where a reviewer flags a specific table
  entry's function as undertested.
- **pnpm 12's `packageManagerDependencies` lockfile addition is a new,
  previously-undocumented (in this repo's own plan) source of "acceptable
  churn"** — worth remembering for any future pnpm major bump: expect a
  purely-additive lockfile diff recording pnpm's own binary plus
  `@pnpm/exe.*` platform packages, distinct from the dependency-resolution
  churn the plan's criteria were originally written to distinguish.

**Promotion note:** the `git checkout -b <new-branch> origin/main` recovery
maneuver (Insight 3) is a good candidate for
`.claude/skills/resolving-pr-comments/SKILL.md`'s "Boundary rules" or a new
step, since it recurs in the exact shape any auto-merge race produces — but
this log defers that promotion to the periodic
`/promoting-work-log-insights` sweep rather than folding it in here, since
this is the first time this specific mechanic has been observed and the
skill's existing "every finding becomes a follow-up PR" framing already
covers the _decision_, just not the _mechanics_.
